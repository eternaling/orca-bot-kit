一件活怎么流下去（主路 + 三条岔路）

橙色=你，蓝色=bot，绿色=worker；除了成功那条主路，失败、能力不符、等你确认三条岔路也画上了

派完就结束回合只是顺利时的一半：worker 可能失败重试、可能卡在等你确认（healthy but waiting for human）、也可能压根没能力碰这份材料。

主路

  1. 你说需求 + 完成标准 + 依赖的本机条件
    要读本机文件、要联网、要某个 CLI 权限，先说；否则 worker 可能「看起来在干，其实碰不到料」。
  2. Bot选执行方式：自己干 / 开 worker / 交给另一个 bot
    小而可当场验证 → 自己做；要隔离、要跑久、要并行、要独立评审 → 开 worker。不是硬门槛，看收益是否盖过派发和验收成本。
  3. Bot派发前先确认对方够得到料易漏
    目标机上有没有文件、有没有工具、agent 类型在不在、模型行不行。--on 选的是 worker 所在的 Orca server，Run 和发起命令仍在当前 Orca server；它不保证 worker 能读到另一台机器上的目录。
  4. Bot写 spec 并派发
    worker-start --repo <项目> --worktree new-child --name <短词> --agent pi --model provider/id --effort high --item <n>；spec 写清范围、不可动的东西、验收证据、交付格式。--worktree 是四值：current / selector / new-child / new-top-level，远程不能用 current（Remote current is invalid.）。目标是 current 或已有工作区时不带 --name/--repo/--base-branch/--display-name/--comment/--setup（会被拒）；--item 不能与 --on 同用（It can't be combined with --on.）。--agent 原文是 such as 引出的开放列举（非穷尽），--effort 取 off/minimal/low/medium/high/xhigh/max。
  5. Worker在选定的工作区里干（新建 / 已有 / current 都可能）：改 → 验证 → 报告（不一定都开 PR）
    一个工作区只放一个写手；多人协作要先划清文件所有权。不一定都开 PR。
  6. Bot不等轮询：靠 Orca 通知，但要分清四种结局
    成功完成就进第 7 步验收；其余三种（失败、等你回答/授权、能力不符）分别走下面三条岔路，不是一律「等它自己好」。
  7. Bot验收：看实际改动 + 测试证据 + 剩余事项
    按风险决定要不要再开一个 reviewer；写的人不该自己给自己判过。验收不过就回到第 4 步改 spec 或派修复，不用重开一件事从头来。
  8. 你看结论 + 拍板；点头之后才清理场地
    验收通过、且目录不再需要（没有待修复审和外部依赖）才清理；实际动手是 bot 跑 orca worktree rm，你只管点头。

拿真实的一次举例：读本机两份 HTML → 选执行方式 → 先确认它读得到 → 派发 → 验收 → 清理。我们第一次就是第 3 步没验，白跑三次（一次自称无权限照写、两次承载被关掉）。

三条岔路

失败 / 卡死

先看 Dispatch 的状态与原因（worker-show 的 state 是 Dispatch 四态 ready / succeeded / failed / stopped，不是 Task 六态），再分开处置：stopReason=lost / liveness unverifiable 先别动——原 agent 可能仍在跑，此时既不授权发信也不授权重试，先 worker-show 判断，不确定就报告不确定；state=failed 或 stopReason=exited 才是进程退出已确认，看原因、需要就 worker-stop。重试 ≠ 复制：--retry-of 配 --task <失败的那个>，且不继承位置，--on / --worktree / --agent（--terminal） 四组都要重述。改了 spec，就是新建一个 Task，不算重试（CLI：--spec creates a new one）——那就只有两条路：要么放弃重试链按新 Task 派，要么不动 spec 去重试。三条兜底：换 agent / 换机器 / 自己接手。不盲目重启。

→ 回主路第 3–4 步，或直接收口

三种收场别搞混：worker-stop 真的停（关终端、带 helper）；worker-abandon 只隔离不碰进程（Retains all possibly-live resources and performs no process or filesystem action.）；worker-release 是完事后的清理（幂等）。要取消 Task：先 stop/abandon，再 task-update --status failed --result cancelled。

等你确认 / 要授权

worker 停下等人类回答时是 healthy，不是失败。该回答就回答（orchestration reply --id <msg_id> --body <text>），该你拍板就变成 Item 的 Needs you。怎么判它真在等人：worker-show --dispatch <id> --full 里的 observation.agentWait——非空就是挂在一个只有人能回答的 prompt 上（带证据来源）；null 表示看过、没在等。

两个坑：waitingOnHuman=unknown 是常态（实测 failed/stopped 也是 unknown），不能当证据；agentWait 只在 --full 里有。另一类不是「等人」而是要授权：用 deny --dispatch <id> --prompt <approval_id> --reason <text> 拒掉，它带着理由继续跑，不是卡死，别去 stop。

→ 回答后它继续；否则挂在你身上

能力不符（这次真发生了）

它没读到原文却照样写报告。最硬的证据是 transcript 自述（worker-read 能看到它原话）；「要求它引用只有读过才知道的细节」是降级判据——引不出只说明它没给可验证证据，不能反过来当成“肯定没读”。注意：这不是 Orca 放错机器——出事的 workspace 都是本机 bot home，问题是 worker 自我误判能力后仍然交付。

→ 停掉，改派能碰到料的 agent/机器

要不要开 worker（不绝对，看这几种情形）

情形怎么选
查一下、回一句、改一行自己做，派发的开销比活大
要动项目代码、要跑很久、要隔离开 worker（新工作区或已有工作区都行）
几件互不相干的事并行开，但并发量按当前容量控，不要一次铺满
要独立第二意见按风险决定开不开 reviewer，不是每次都开
要等外部（CI / 别人评审 / 到点）建 automation 等待 + 留 Item 记账；能用什么触发看 trigger-options
整件事该另一个 bot 负责--type handoff 连责任一起交；只是请教用 question，只同步用 status

口径 Item 和 worker 都是按需工具；bot 之间靠 handoff / question / status 交接，不按项目划界。
